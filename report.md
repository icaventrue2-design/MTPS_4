# Отчёт по практической работе №4: Мокирование в тестировании
**Вариант 1: Мокирование HTTP-API (платёжный шлюз)**

---

## 1. Анализ подхода и выбранная стратегия

### a. Почему была выбрана конкретная стратегия мокирования
Для тестирования класса `PaymentService` был выбран подход изоляции внешних HTTP-запросов с использованием библиотеки `unittest.mock.patch`. Так как класс напрямую обращается к стороннему API платёжного шлюза через сетевые HTTP-вызовы, выполнение реальных запросов во время юнит-тестов недопустимо:
- Реальное API может быть недоступно или нестабильно.
- Тестовые списывания средств требуют реальных учетных данных и занимают много времени.
- Запросы создают побочные эффекты на стороне внешнего сервиса.

### b. Замокированные артефакты
- **Замокированный объект**: Функция `requests.post` внутри модуля `payment_service`.
- **Причина**: Изоляция тестируемого метода `process_payment()` от сетевого слоя, подмена ответа сервиса (JSON-тела и HTTP-статуса) и симуляция исключительных ситуаций (`requests.Timeout`, `requests.ConnectionError`).

### c. Плюсы и минусы мокирования в данном случае
* **Плюсы**:
  - **Скорость и изолированность**: Тесты выполняются за миллисекунды и не зависят от интернета.
  - **Воспроизводимость**: Возможность легко воспроизвести редкие негативные сценарии (таймаут, сетевой сбой, отказ банка).
  - **Верификация вызова**: Проверка точных параметров запроса (URL, JSON-тело, заголовки, таймаут).
* **Минусы**:
  - **Ложное чувство безопасности**: Если стороннее API изменит формат ответа или заголовков, замокированный тест останется «зеленым», но реальная интеграция сломается.

### d. Альтернативные подходы
- **Responses / HTTPretty**: Специализированные библиотеки для перехвата HTTP-запросов на уровне библиотеки `requests`.
- **WireMock / MockWebServer**: Запуск локального mock-сервера, принимающего реальные HTTP-запросы (полезно при интеграционном тестировании).
- **TestContainers**: Использование контейнеров с заглушкой API для сквозного тестирования.

## 2. Ответы на контрольные вопросы

### 1. В чём разница между mock и stub? Приведите пример.
- **Stub (заглушка)** — объект, предоставляющий готовые зафиксированные ответы на вызовы во время теста. Он не проверяет, как именно его вызывали.  
  *Пример*: Заглушка ответа `requests.post`, возвращающая статус 200 и JSON `{"status": "success"}`.
- **Mock (имитация)** — объект, который не только возвращает фейковые данные, но и регистрирует информацию о вызовах (параметры, количество вызовов). В конце теста проверяется взаимодействие с ним.  
  *Пример*: Проверка `mock_post.assert_called_once_with(...)`, подтверждающая отправку точных заголовков авторизации и правильной суммы.

### 2. Может ли избыточное мокирование привести к «зелёным, но бесполезным» тестам? Почему?
Да, может. Это происходит, когда тесты завязываются на внутреннюю реализацию кода, а не на его поведение. Если замокировать слишком много внутренних методов или сторонних ответов с нереалистичными данными, тест успешно пройдет, но не будет отражать реальную работу системы. При изменении контракта API или внутренней структуры код сломается в продакшене, хотя тесты останутся «зелёными».

### 3. Как проверить, что мок-объект был вызван именно с такими-то параметрами?
В Python с помощью фреймворка `unittest.mock` используются методы проверки:
- `mock.assert_called_once_with(*args, **kwargs)` — проверяет, что вызов был ровно один раз с конкретными аргументами.
- `mock.assert_called_with(*args, **kwargs)` — проверяет аргументы последнего вызова.

### 4. Как избежать «хрупкости тестов» при мокировании внутренних деталей реализации?
- Мокировать **только внешние зависимости** (границы системы: БД, HTTP API, файловая система), а не внутренние методы тестируемого класса.
- Тестировать **поведение и публичный контракт** (входные и выходные данные), а не последовательность внутренних вызовов.
- Использовать интеграционные тесты (с TestContainers или in-memory БД) там, где изоляция unit-тестов теряет смысл.
